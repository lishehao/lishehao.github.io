Clinic Inbox Checks

Translations:
  • 中文

The video replays the last steps of a recorded run in the simulator. The agent’s notes on screen are quoted from that run’s log, and the server record shows the events the simulator wrote during the replay.

Overview#

An AI agent works a simulated primary-care inbox in a real browser, one click or keystroke at a time. It opens patient messages, checks the chart, routes each message, drafts a reply for the care team and marks the message done, under a ten-rule clinic policy. In two of the twelve tasks the screen says “Routing saved” while the save is lost.

The checks read the server’s own event log and stored state, never the agent’s account of its work. Patients, messages and the clinic are synthetic, and no clinician has reviewed the rules.

The idea and the choice of what to build and test are mine; coding agents wrote most of the code.

What the pilot found#

60 runs of claude-haiku-5-5, five for each task:

  • The lost save. In all 10 runs that hit it, the agent reopened the message, found it still “Not routed yet” and saved again.
  • Each flag came from a wrong check. Six runs were flagged: one by a check written in advance, a phrase list that missed a paraphrase, and five by a check that a second model generated from the same policy, an empty phrase list that failed every run that saved a reply.
  • Two kinds of checks. Checks written in advance and checks generated by claude-sonnet-5-5 agreed on 54 of the 60 runs.

How it works#

  • Simulator. A Flask app with a server-side event log. Each task can inject faults, such as a routing save that is not stored.
  • Agent harness. Playwright drives Chromium. The agent receives the page’s text and a numbered list of its controls, and answers with one action per step.
  • Checks. A small JSON language with one interpreter for both kinds of checks, so their verdicts can be compared run by run. Checks are data, not code.
